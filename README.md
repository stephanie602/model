# 实时语音助手 · Windows 版

麦克风 → 降噪 → 能量 VAD 分句 → ASR → 终端实时文字 →（可选）LLM 回答 → TTS 朗读。

```
sounddevice(WASAPI) → AGC 增益 →┬→ [唤醒词闸] KWS 3.3M
                                 └→ GTCRN 降噪 → Silero VAD → SenseVoice ──┐
                                                                           ↓
                                 扬声器 ← Matcha TTS ← llama-server(HTTP)
```

唤醒词吃的是**未降噪**的音频——GTCRN 会把弱语音当噪声削掉，对只有 3.3 M 参数的 KWS
是致命的；而 VAD 那一路恰恰离不开降噪。两边要的东西相反，所以在 AGC 之后分叉。

语音那三块（ASR / 降噪 / TTS）全部由 **sherpa-onnx** 一个库提供，纯 CPU，无需显卡。
LLM 是**独立的 llama-server.exe 进程**，只通过 HTTP 交互 —— 换模型、换后端、甚至挪到
另一台机器上，语音这边都不用改代码。

## 快速开始

```powershell
# 0) 只在第一次:放开脚本执行权限（只影响当前用户，不需要管理员）
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

# 1) 装环境 + 下模型（国内网络加 -CN）
.\setup_windows.ps1

# 2) 起 LLM server —— 这个窗口一直开着
.\start_llm.ps1

# 3) 另开一个窗口，跑语音链路
.venv\Scripts\python.exe realtime_asr.py --denoise --chat --speak
```

要求：Windows 10 1803 以上、64 位 Python 3.9–3.12、约 4 GB 磁盘。

## 按顺序自检

出问题时别一上来就跑整条链路，逐段验证好定位：

| 步骤 | 命令 | 验证什么 |
|---|---|---|
| 1 | `.venv\Scripts\python.exe realtime_asr.py --list-devices` | 系统认不认得到麦克风 |
| 2 | `.venv\Scripts\python.exe realtime_asr.py --denoise` | 降噪 + 识别（不联网、不用 LLM） |
| 3 | `.venv\Scripts\python.exe tts.py "你好,我是语音助手"` | 合成 + 播放 |
| 4 | `curl.exe http://127.0.0.1:8080/v1/models` | LLM server 起来没有 |
| 5 | `.venv\Scripts\python.exe wakeword.py` | 唤醒词（对着麦克风说"你好小智"） |
| 6 | `.venv\Scripts\python.exe realtime_asr.py --denoise --chat --speak` | 整条链路 |

设备列表里同一个物理麦克风通常会出现好几次（MME / DirectSound / WASAPI）。
**优先挑 WASAPI 那一条**：延迟最低，而且更容易协商到 16 kHz —— `--denoise` 要求
输入必须是 16 kHz（GTCRN 是固定采样率的流式模型，中间插不了重采样）。

## 麦克风增益（AGC）

```powershell
realtime_asr.py                      # 默认就开着（--gain auto）
realtime_asr.py --gain off           # 关掉
realtime_asr.py --gain 8             # 固定 8 倍
```

**先看这个再怀疑模型。** 板载麦克风的电平常常低得离谱：实测这块板子正常说话录出来
峰值只有 0.033–0.056（正常应该 0.1–0.4），低 20–30 dB。这个电平会同时卡死两道阈值 ——
VAD 的下限 `THRESHOLD_MIN` 是 0.006，和说话本身一样大，半句话被判成静音。

同一批真人录音，唤醒词检出：

| | 检出 |
|---|---|
| 原始电平 | **0 / 3** |
| 过 AGC（补 9–15 倍） | **3 / 3** |

整条链路上的表现：唤醒从"喊到第三遍才醒"变成"第一遍就醒"（36 块 → 12 块），
`关闭点灯` 也变回了 `关闭电灯`。

AGC 只治"长期电平不对"，不压动态。电平已经正常的输入**一个样点都不动**：

| 输入 | AGC 行为 |
|---|---|
| 峰值 0.05 的真人录音 | 补到 9–15 倍 |
| 峰值 0.34 的正常录音 | **1.00x，输出与输入逐样点相同** |
| 30 秒纯底噪 | 1.00x（不放大噪声，否则 VAD 会瞎掉） |
| 已经满量程的输入 | 1.00x（不再往上推） |

单独看一段录音的电平：

```powershell
python gain.py 某段录音.wav                 # 只分析
python gain.py 某段录音.wav -o 处理后.wav    # 写出处理后的音频，可以听
```

**硬件能调就先调硬件**：设置 → 系统 → 声音 → 输入 → 音量拉到 80–100，再进
「设备属性 → 其他设备属性 → 级别」把「麦克风加强」开到 +20 dB。AGC 放大的是已经
被采样丢掉精度的信号，录得响一开始就更好。电平低于 0.06 时程序退出会打印提醒。

## 唤醒词（省 CPU 的主力开关，默认关）

```powershell
realtime_asr.py --wake --chat --speak
```

**默认不用唤醒词**：开口就能问，不用先喊"你好小智"。设备场景里操作工是随手一问的
（"现在温度多少"），中间插一句唤醒词很别扭；报警之后更是——刚播完"传送带卡住"，
还要求先喊一遍才能问"怎么处理"，等于把最要紧的那一句挡在门外。
代价是麦克风一直在解，安静车间里多花的 CPU 有限；**现场一直有人说话、或者机器要长时间
待机**时，加 `--wake` 把这道闸门装回去（报警会自动开闸，不影响接着追问）。

加上 `--wake` 之后，**没听到"你好小智"之前整条识别链路是停的** —— 只有一个
3.3 MB 的 KWS 模型在跑，1 线程 RTF≈0.007（不到一个核的 1%）。对比一下：不开唤醒词时
SenseVoice 每 1.2 秒解一次临时结果、每句再解一次定稿，安静房间里底噪偶尔顶过 VAD
阈值也会白解一次。

KWS 前面还有一层能量闸（默认开）：安静的块连特征都不提，直接跳过，安静房间里能再
挡掉八九成。跳过时留 0.3 秒预滚，声音一起来先补喂进去，不会咬掉唤醒词的第一个字。

唤醒之后进入连续对话，`--wake-timeout`（默认 15 秒）没人说话就自动睡回去，
一问一答之间不用反复叫醒。

```powershell
realtime_asr.py --wake --wake-word 小爱同学          # 换唤醒词，可以给多个
realtime_asr.py --wake --wake-threshold 0.4          # 误唤醒多就调高，叫不醒就调低（默认 0.25）
realtime_asr.py --wake --wake-timeout 30             # 醒着的时长
realtime_asr.py --wake --wake-reply ""               # 唤醒时不出声应答（默认念"我在"）
realtime_asr.py --wake --no-wake-energy-gate         # 关掉能量闸（对比 CPU 用）
realtime_asr.py --wake --wake-mode text              # 没下 KWS 模型时的兜底，见下
```

唤醒词挑**四个字、发音别太常见**的。两个字的（"小智"）误唤醒会非常多。
换了唤醒词先单独测：`wakeword.py --keywords 小爱同学`，喊十次数一下中几次。

### 默认参数是实测出来的，别照抄 sherpa-onnx 的默认值

拿一段 60 秒双麦真人录音（持续噪声，喊了 17 次"你好小智"）扫出来的：

| 配置 | 检出 | RTF |
|---|---|---|
| sherpa-onnx 原始默认（int8 / score 1.5 / 阈值 0.25 / beam 4） | **1 / 17** | 0.010 |
| 换 fp32 | 8 / 17 | 0.011 |
| + score 3.0、阈值 0.1 | 11 / 17 | 0.011 |
| + beam 10（现在的默认） | **15 / 17** | 0.012 |

三处反直觉的地方：

- **fp32 优先，不是 int8。** 这个模型只有 3.3 M 参数，量化误差占比太大，噪声里本来就不多的声学证据直接被抹平（3 → 8 次）。省那十几 MB 内存换漏检不值。ASR 那边 int8 无所谓，是因为模型大 60 倍。
- **beam 不能省。** 4 → 10 让检出从 11 涨到 15，RTF 只从 0.0114 涨到 0.0121。噪声里关键词的路径很容易在中途被别的词挤掉。
- **命中后不能 `reset_stream`。** 它会把编码器上下文一起清掉，连着喊时下一次要从冷状态重起，15 次掉到 13 次。改成 0.8 秒去抖防重复报。

同一段录音里的干扰内容（数数"1234567891…"、"这条线是不是要慢看一点"）一次都没误触发。

**两种模式**：

| | `kws`（默认） | `text` |
|---|---|---|
| 怎么判 | 专用 KWS 模型直接听音频 | 拿 ASR 的识别结果按拼音比对 |
| 省 CPU | ✅ 睡着时 ASR 一次都不解 | ❌ ASR 照跑，省的只是 LLM 和 TTS |
| 要下模型 | 要（3.3 MB，`setup_windows.ps1` 会下） | 不要 |
| 唤醒词后面接着说命令 | 支持（"你好小智" → 停顿 → 命令 更稳） | 支持（"你好小智打开电灯" 一句话办完） |

`text` 模式按拼音比对而不是按字面：ASR 把"你好小智"听成"你好小纸 / 你好晓知"是常态，
声母韵母却基本不会错，去掉声调再比就都收得下。

`--wake` 和 `--denoise` 一样要求输入是 16 kHz（KWS 是流式模型，中间插不了重采样）。
设备给不了就换 WASAPI 那条输入，或者退回 `--wake-mode text`。

## 噪声环境下句子被切碎 → 换 VAD

这是默认行为，写在这里是因为它值得知道：**分句用的是 Silero 神经网络 VAD**（640 KB），
不是能量阈值。

纯能量 VAD 在噪声房间里会彻底失效，机制是两个常数打架：触发阈值 = 底噪 × 3，
夹在 0.006–0.05 之间。底噪 RMS 到 0.02 时，×3 = 0.06 被上限钳到 0.05；而语音块的
RMS 只有 0.042–0.059——**和阈值重叠**。结果是一句话里只有最响的那个音节能过线，
从半句话中间开始切，ASR 只看到残片。

同一段 60 秒录音（人声清楚、背景噪声持续），同一个 ASR：

| VAD | 判为人声 | 识别结果 |
|---|---|---|
| `--vad energy` | 6 / 600 块 | 是。你好小志。一样无所谓。要小智。是。 |
| `--vad silero`（默认） | 303 / 625 块 | 你好小智你好小智…**这个调这条线是不是要迈开一点**，他都一样，无所谓。…差不多了。 |

上限 0.05 不能简单调高——调高了正常音量的说话也过不了线。出路是别再用能量判人声：
噪声和人声的能量本来就可以一样大，这个信息量不够。Silero 看的是频谱结构，
一句话在它眼里和一台风扇完全不同，不管谁更响。代价 RTF 0.003。

```powershell
realtime_asr.py --vad energy          # 退回能量判定（对照实验用）
realtime_asr.py --vad-threshold 0.3   # Silero 阈值 0-1，默认 0.5
vad.py test.wav                       # 单独测：两种 VAD 并排画出人声区间
```

`--vad-threshold` 调低会把气声、远处说话收进来；调高会咬掉句子开头的轻声字。

## 噪声下听不准命令 → 靠 KWS，不是靠换 ASR

同一段真人录音混不同信噪比，整段丢给 ASR 直接解码，看命令还认不认得出来：

| 信噪比 | SenseVoice 出的字 | 命令还在吗 |
|---|---|---|
| 干净 | 打开电灯，关闭电灯。 | ✅ 两条 |
| 15 dB | 小打开电灯，关闭电。 | ✅ 两条（拼音匹配捞回来的） |
| 10 dB | 小打开电，关闭电。 | ⚠️ 只剩一条 |
| 5 dB | 小打开关闭。 | ❌ 全丢 |
| 0 dB | 好小小打开关闭。 | ❌ 全丢 |

5 dB 以下 ASR 那条路就废了——字被噪声吃掉，拼音匹配再聪明也无米下锅。
**这时候还站得住的只有命令 KWS**：它不经过 ASR，直接在音频里找那几个词，
实测同一段 5 dB 录音 ASR 0/2、KWS 2/2。所以噪声环境下这两条都要开（默认就是开的）：

```powershell
realtime_asr.py --commands hotwords.txt --command-kws
```

**代价是它只认表里的词**，所以 `hotwords.txt` 必须是你现场真会说的那些话。
本项目那张表已经按包装机场景写好了：问温度/速度/产量的几种问法、
工人处理完故障回话的几种说法（"料加好了""清理干净了"）、开停机。
改这张表不用改代码，KWS 和拼音匹配两边同时生效。

试过换成 zipformer + 热词（transducer 能在解码时给热词加分，SenseVoice 不行）：
固定命令确实更抗噪——5 dB 下两条命令全中，0 dB 还能中一条。但**自由说话明显变差**：
同一段 60 秒噪声录音，SenseVoice 转出了整句"这个调这条线是不是要慢看一点"，
zipformer 只剩"姚小志五六七八九十四差不多了"。这套要同时应付固定命令和自由问答，
所以留 SenseVoice，抗噪交给 KWS 那一路。

## 识别不准时：先做麦克风体检

```powershell
realtime_asr.py --mic-check                        # 录 10 秒，一次量完
realtime_asr.py --mic-check 20 --save-check c.wav  # 录 20 秒并存下来自己听
```

"话说了没反应"有四种原因，症状**长得一模一样**：说话太轻、离得太远、噪声太大、
驱动丢块。一条条试要花掉一下午，这个命令一次把四个量都测出来：

```
输入峰值   0.054      (正常 0.1-0.4)
底噪 RMS   0.0004
信噪比     28 dB
AGC 补到   9.2x
采集丢块   0 次
唤醒词     10 秒里检出 3 次
```

| 量 | 想要的值 | 不对时怎么办 |
|---|---|---|
| 输入峰值 | 0.1–0.4 | 低了：系统输入音量拉到 80–100 + 麦克风加强 +20 dB。AGC 能补，但补的是已经丢了精度的信号 |
| 信噪比 | ≥ 20 dB | **软件补不回来**——放大是连噪声一起放大。见下面 |
| 采集丢块 | 0 | 非 0 说明 CPU 被抢光，音频是真丢了：LLM 的 `-Threads` 调小，或加 `--no-partial` |
| 唤醒词 | 喊几次中几次 | 前三项都正常还是 0，把录音存下来听一遍 |

调完麦克风位置再跑一遍，直接看数字有没有变好，不用靠感觉。

### 信噪比是唯一补不回来的那个量

增益、降噪、调参数都救不了它。能动的只有采集端：

- **距离减半 ≈ +6 dB。** 从 50 cm 挪到 25 cm 就是 6 dB，挪到 10 cm 是 14 dB。这是最有效的一招
- **指向性麦克风**（心形）比板载全向麦克风好 6–10 dB，几十块钱的 USB 领夹麦就够
- **麦克风背对噪声源**，别让风扇/空调/音箱在麦克风正前方
- **关掉 Windows 的"音频增强"**：设备属性 → 高级 → 取消"启用音频增强"。板载麦克风阵列的
  厂商处理有时反而把远场人声压得更狠

参考实测：一段信噪比 28 dB 的录音唤醒词 3/3 全中；同一支麦克风在噪声环境下录的
（信噪比 5–7 dB、人耳听都只听得清一两个字），唤醒词 0 检出、SenseVoice 每句只吐一个字。
到那个程度换什么模型、调什么参数都没用，得先把录音本身弄干净。

## 常用参数

```powershell
# 指定输入设备
realtime_asr.py --device 3

# 只要定稿结果，省一半算力（低配机器上先试这个）
realtime_asr.py --no-partial

# 粤语
realtime_asr.py --language Cantonese

# 换回 Kokoro（音色多、听感更好，但这类 CPU 上合成比实时还慢，见下）
realtime_asr.py --speak --tts-model models\kokoro-multi-lang-v1_0 --voice zm_yunxi

# 出声更快：攒 6 个字就切一句去合成（代价是句子偏碎）
realtime_asr.py --chat --speak --tts-min-clause 6

# LLM 放在另一台机器上
realtime_asr.py --chat --chat-url http://192.168.1.10:8080/v1

# 嫌延迟大先看瓶颈在哪，别凭感觉调参数
realtime_asr.py --chat --speak --timing

# 没有麦克风时，用音频文件模拟实时输入（wav/flac/ogg）
realtime_asr.py --simulate test.wav
```

`--timing` 打出来的 **RTF** 是最该看的数：合成/识别 1 秒音频花了几秒。
> 1 就说明这一环跟不上实时，句子会越积越多。ASR 的 RTF 高就加 `--num-threads`，
TTS 的高就加 `--tts-threads`，两个都高就说明 CPU 被 llama-server 抢光了 ——
`start_llm.ps1 -Threads` 调小，或者换 `-Model 1.7b`。

## TTS 用 Matcha，不是 Kokoro

合成慢在语音助手里是致命的：只要合成 1 秒音频要花 1 秒以上，句子就会越排越多，
声音永远追不上文字——表现是"屏幕上早写完了，喇叭还在念第一句"。

同一台 i7-13620H 上量的同一句话：

| 文本 | Kokoro | Matcha + vocos |
|---|---|---|
| 「正常，」 | 1.98s | **0.05s** |
| 「封口温度一百六十八度。」 | 5.90s | **0.52s** |
| 报警那句（21 字） | 11.48s | **3.56s** |
| 开机预合成 50 条固定话术 | 128s | **12s** |

代价：Matcha 中文只有一个音色（Kokoro 有 8 个），听感素一点。要换回去：

```powershell
realtime_asr.py --speak --tts-model models\kokoro-multi-lang-v1_0 --voice zf_xiaoxiao
```

模型类型是**按目录里的文件认的**，不看目录名——`model-steps-*.onnx` 就是 Matcha，
`model.onnx` + `voices.bin` 就是 Kokoro。Matcha 的声码器（`vocos-*.onnx`）是单独一个
文件，放模型目录里或 `models\` 下都行，多个 Matcha 模型共用它。

## LLM 那一侧

```powershell
.\start_llm.ps1                  # Qwen3-4B Q4_K_M，平衡
.\start_llm.ps1 -Model 1.7b      # 明显更跟手，质量差一点
.\start_llm.ps1 -Backend vulkan  # 有独显/核显就用它，比纯 CPU 快好几倍
.\start_llm.ps1 -Port 8081       # 换端口（语音那边跟着加 --chat-url）
.\start_llm.ps1 -CN              # 模型走 hf-mirror
```

没有 `llama-server.exe` 时脚本会自动去 GitHub 下官方预编译包，解压即用，不用自己编译。
`-Backend vulkan` 不挑显卡厂商、不用装 CUDA，有独显或者稍新的核显都值得试一下。

## 包装机场景（设备报警 + 状态问答）

演示里的两个方向是分开走的，因为对可靠性的要求不一样。

**机器主动说 —— 按键触发**

| 按键 | 播报 |
|---|---|
| `1` | **报警**·缺原材料：注意，包装机原材料不足，请及时补充原材料。 |
| `2` | **报警**·传送带异物堵塞：注意，传送带有异物卡住，设备已自动停机，请清理杂物后重新启动。 |
| `3` | **解除** 第 1 条：原材料已补充，料位恢复正常，设备继续运行。 |
| `4` | **解除** 第 2 条：传送带杂物已清理，设备已重新启动，恢复正常运行。 |
| `空格` | 下一条报警，按顺序循环（一路演下去用这个，不用挑键） |
| `R` | 全部解除 |

数字键前一半放报警、后一半解除对应那一条；`ALERTS` 加到三条就自动变成 `1-3` 报警、`4-6` 解除。

**按条解除，不是一把全清**：两条报警可以同时挂着（缺料还没补，传送带又卡了），
这时候按 `3` 只解除缺料，设备仍然停机——全清会连没处理的那条一起抹掉，状态就和现场对不上了。
按了一条本来没响的报警的解除键，只在终端提示一行、**不出声**：
念一句"已恢复正常"会让人以为刚才真报过警。

解除必须有播报——报警响过而没有收尾，操作工不知道该不该继续等，现场最怕"报了警然后没下文"。
解除词说的是**什么解除了**（"原材料已补充" / "杂物已清理"），不是笼统的"已恢复正常"：
两条同时挂着时，光说恢复听不出好的是哪一条。

解除同时把状态推回正常：刚才停机时问速度答"设备当前已停机，速度为零"，
解除之后再问就是"每分钟 42 包"。停机期间产量是冻住的，不会凭空多出几十包。

要加报警只改 `machine.py` 里的 `ALERTS` 列表（一条报警自带 `speech` 和 `cleared` 两句话），
热键提示行和数字键会自动跟着长。

报警**不经过 LLM**：话术是安全相关的固定内容，必须每次一字不差，也必须立刻出声，
不能等一轮生成。它会打断正在念的任何内容，并顺手把唤醒闸门打开——
报警之后用户十有八九要接着问，这时候还要求先喊一遍"你好小智"很别扭。

报警会真的改状态：触发第二条以后再问速度，答的是"设备当前已停机，速度为零"，
而不是"每分钟 42 包"。

**工人回话 —— 语音解除报警**

报警响的时候工人手上多半正忙着（在上料、在掏传送带里的杂物），回来按键不现实。
说一句就撤：

| 报警 | 说这些都算 |
|---|---|
| 缺原材料 | 料加好了 / 补料完成 / 上料完成 / 原材料补充完了 |
| 传送带堵塞 | 清理干净了 / 杂物清掉了 / 异物取出来了 / 重新启动了 |
| 任意一条（只挂着一条时） | 好了 / 处理完了 / 搞定 / 恢复了 |

三条规矩，都是为了别乱撤：**没有报警挂着时一律不动**（日常对话里一句"好了"不会
莫名其妙播解除词）；**专用词优先于通用词**（堵塞报警挂着时说"料加好了"，里面虽然有
"好了"，但它说的是料，不解堵塞）；**两条都挂着时通用词不认**，得说清是哪一条。

**用户主动问 —— 直接说**

| 问 | 答 |
|---|---|
| 机器目前温度和速度是什么 | 当前封口温度 168.2 摄氏度，包装速度 每分钟 42 包。 |
| 今天我们完成了多少个包装 | 今天已经完成 3874 个包装。（准确到个位） |

问法要点到设备才接管：「机器怎么样」「这个温度正常吗」算，「今天怎么样」「中午吃什么」
不算，照旧交给 LLM——不然什么问题都会被答成"封口温度一百六十八度、速度四十二包"。
点名了具体哪一项就只答那一项，不把三个数一起倒出来。

这两类问题的答案是**数字**，让 4B 模型转述只会多一道出错的机会。所以先按拼音把问题
对到一张查询表上，命中就用真实状态拼一句话直接回答，省掉整整一轮生成（快一两秒）。
按拼音而不是汉字，理由和命令词一样——噪声下"温度"会被识别成"文度"、"包装"成"包妆"，
汉字比对全漏，拼音全中。

问得绕的（"这个温度正常吗""还能撑多久"）对不上查询表，照旧交给 LLM；
但 LLM 的系统提示里每次请求都会**现取**一份同样的状态，所以它手里也是真数字，
不会自己编。本地答掉的那一轮会补记进对话历史，接着追问"那怎么处理"时它接得上。

状态现在是模拟的（温度在设定值附近漂，产量按节拍涨）。接真机时改 `machine.py` 里的
`Machine.snapshot()` 去读 PLC / MES，把 `next_alert()` 挂到 PLC 的报警回调上，
上面两条链路一行都不用动。

```powershell
.venv\Scripts\python.exe machine.py                  # 打一遍状态和报警文案
.venv\Scripts\python.exe machine.py "现在温度多少"   # 试问答匹配
.venv\Scripts\python.exe realtime_asr.py --no-machine # 关掉这个场景
```

## 相比原来的 Mac / RK3588 版少了什么

这个目录是从双后端（macOS MLX + RK3588 Linux）版本里剥出来的纯 Windows 版，
以下东西**在 Windows 上不存在对应实现**，已经整体删掉，不是"暂时没做"：

| 删掉的 | 原来的作用 | Windows 上的替代 |
|---|---|---|
| MLX / FireRedASR2 | Mac 上的 ASR，覆盖 20 多种方言 | SenseVoice —— 中/英/日/韩/粤，**方言只有粤语** |
| MLX Kokoro | Mac 上的神经 TTS | Matcha（快得多，见下）；Kokoro 也还能用，`--tts-model` 指过去 |
| DeepFilterNet2 | Mac 上的降噪 | GTCRN，真流式，几乎不占 CPU |
| macOS `say` | 零依赖的兜底 TTS | 无（Kokoro 本身就够轻） |
| RKNN / librknnrt | RK3588 的 NPU 加速 | 无，纯 CPU；模型包里带 `.rknn` 的在这儿用不了 |
| 进程内 MLX LLM | Mac 上进程内加载 Qwen3 | llama-server.exe，HTTP |
| `nbest.py` | FireRedASR2 的 n-best 诊断 | 无 —— SenseVoice 是 CTC 模型，没有 decoder beam 可看 |

**最大的一处退让是方言**：FireRedASR2 只有 MLX 实现（没有 ONNX 导出），
四川话、上海话这些在这儿会退化成"按普通话猜"，错字会明显变多。普通话和粤语不受影响。

## 排障

**识别一直没字，也不报错。**
多半是麦克风权限：设置 → 隐私和安全性 → 麦克风，"麦克风访问"和"让桌面应用访问麦克风"
都要打开。关着的时候 `sounddevice` 看得到设备，录出来却是一整条静音，什么错都不报。

**中文输出是乱码 / 方框。**
用 Windows Terminal 或 PowerShell 7。老的 conhost 即使代码页对了，字体也常常缺字。
（程序自己已经把 stdout 切成 UTF-8 并打开了 ANSI 转义，这一步不用手动设。）

**助手自己跟自己聊起来。**
喇叭的声音被麦克风录回去了。默认的麦克风闸门（朗读时静音 VAD）应该拦得住，
如果还是发生，说明音量太大或者混响太重：调小音量，或者戴耳机再加 `--no-mic-gate`。

**噪声环境下每句都是 15 秒。**
这是能量 VAD 被底噪钳死了——底噪 RMS 抬到 0.18 时阈值被上限卡在 0.05，于是永远判定
"有人在说话"，每句都是撞 `--max-segment` 强制切出来的。加 `--denoise`，
或者用 `--threshold` 手动固定一个阈值。

**`llama-server.exe` 双击闪退 / 报 0xc000007b。**
解压不完整（`.dll` 必须和 `.exe` 在同一目录），或者缺 VC++ 运行库：
装 <https://aka.ms/vs/17/release/vc_redist.x64.exe>。

**唤醒词叫不醒 / 老是自己醒。**
先单独跑 `wakeword.py` 数命中率，别在整条链路里调。叫不醒就把 `--wake-threshold`
往 0.15 调，误唤醒多就往 0.4 调。这个模型是**拼音建模**的，唤醒词里有生僻字不要紧，
拼音进得去就行；真编不进词表的话启动时会明确打出来是哪几个音，不会闷声跳过。

**识别时准时不准，说话声明显要凑近麦克风才行。**
麦克风电平太低。先跑 `python gain.py <一段录音>.wav` 看峰值：低于 0.06 就是这个问题
（AGC 默认已经在补，但硬件调好效果更好）。用 `--save-segments captured` 存几句下来分析最直接。
